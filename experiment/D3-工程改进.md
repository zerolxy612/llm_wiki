# D3：导入任务状态的真实表达

## 问题与复现

1. 基线进度使用 `(成功 + 失败 + 取消) / 总数`，同时把该数字标作完成。8 个任务里 3 成功、2 失败、1 取消时，界面会显示 6/8 complete，容易被理解为六份文档已成功入库。
2. 暂停和缺少模型配置时，pending 数大于零仍会使面板图标旋转。pending 上的服务商限流错误不显示，最终 failed 错误又被截断。
3. 空闲时调用暂停/恢复只修改模块状态，没有写入队列，也没有发出订阅通知。UI 依赖推送而非轮询，因此不会立即刷新。
4. 原生验收时发现完成后的面板无法保持收起：自动展开逻辑监听用户展开状态，用户刚收起就又被已有任务记录展开。

第 3 项已用真实队列模块复现。修复前期望收到 `[false, true, false]`，实际只有初始 `[false]`，见 `evidence/D3-before.txt`。

## 改动

- 从队列事实派生配置阻塞、暂停、处理中、等待、需要处理、完成六种展示状态。
- 成功、失败、取消分别着色并显示数字；`aria-valuenow` 只表示成功数，`aria-valuetext` 包含完整结果计数。
- 保留已有批量取消、重试和任务优先级功能；停止后仍可按原入口重试。
- pending/failed 等状态只要有错误就可以展开完整原因，来源路径可通过悬停查看。
- 暂停/恢复显式通知订阅者，空闲时也生效。没有新增计时轮询。
- 自动展开只在首次出现工作或新的运行任务开始时触发，保留用户手动收起状态；修正暂停提示，使其明确表达请求中止未完成任务。
- 中文、英文、意大利文、俄文保持键和插值变量一致。

## 手动验收

1. 未填 Key 时打开实验项目：预期显示等待配置及设置/继续提示，图标停止旋转。
2. 配好模型后启动导入，暂停：预期立即显示暂停，恢复后继续，不丢失队列。
3. 取消一个等待任务：取消数增加，成功数不增加，仍可重新开始。
4. 模型错误发生时展开原因：完整内容可读，不再只能看一行截断信息。
5. 使用错误凭据仅做一次受控失败观察；随后恢复凭据并重试，检查来源和生成文件。不要为演示反复发起无意义付费请求。
6. 使用读屏语义或开发者工具确认进度条：有失败/取消时成功值不等于终态总数。

## 技术取舍

选择修正状态解释与通知机制，范围能在一天内完成和回归。未引入新任务数据库、事件总线、进度百分比估算或回滚系统。阶段详情继续使用现有活动记录；真实的 token 百分比和 ETA 没有可靠依据，故不展示。

进度条填充仍包含三类终态，必须结合颜色和文字解释；成功数才是入库结果。计数是当前会话的队列统计，成功任务在持久化队列中会被移除，因此不应称作跨重启的完整审计记录。取消后的部分原子写入保留，上游不提供跨文件事务回滚；本次改动不改变该边界。

## 可以怎样讲

“我研究了一个将原始文档编译成持久 Wiki、再结合检索回答问题的开源项目。我的改动聚焦长任务状态：原界面把失败和取消也算作完成，暂停还存在漏通知。我将结果计数和运行状态分开，补充完整失败原因，并用修复前失败、修复后通过的队列测试验证。核心 AI 架构属于上游；模型质量和成本我按独立实验记录，不把功能跑通包装成生产收益。”
